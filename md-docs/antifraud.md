# Модуль антифрода

Пакет `internal/antifraud`. Задача — обнаружить раздачу подписки на большое число устройств/
людей и временно ограничить доступ, не трогая при этом конфигурацию на диске.

## 1. Принцип работы

Xray пишет access-лог в tmpfs (`/dev/shm/xray-access.log`). Модуль читает лог построчно,
извлекает пару «IP → email» и считает количество **уникальных IP** пользователя в скользящем
окне. Если счётчик превышает динамический порог, применяется **софт-бан**: пользователь
удаляется из памяти работающего Xray, но остаётся в `config.json` и в базе.

```
Xray access.log (tmpfs)
        │
   [rotator]  — следит за размером и возрастом файла, переименовывает и сигналит tailer'у
        │
   [tailer]   — читает файл без лишних аллокаций, шлёт события в канал (буфер 1000)
        │
   [analyzer] — считает уникальные IP, сравнивает с порогом, выносит бан
        │
   [ip cleaner] — раз в 30 секунд вычищает IP старше TTL
   [unban cleaner] — раз в 15 секунд снимает истёкшие баны
```

Все пять горутин запускаются из `Module.Run(ctx)` и завершаются по отмене контекста.

## 2. Динамический порог

```
порог = anti_fraud.max_ips × subscriptions.max_devices
```

Значения `max_devices` держатся в кеше, обновляемом раз в 2 минуты одним запросом к БД;
при промахе кеша используется безопасное значение `1`, а реальное подтягивается фоново.
Пример из лога: `7 unique IPs in 5m0s window (limit 6 = 3 base × 2 devices)`.

## 3. Приватность

IP-адреса **не хранятся в открытом виде**: `State` держит HMAC-SHA-256 хеши, посоленные
значением `anti_fraud.salt_secret` (либо общекластерной константой, если соль не задана).
Слейв хеширует IP до отправки мастеру, поэтому «сырые» адреса не покидают узел.

> Важно: соль должна быть **одинаковой** на всех узлах кластера, иначе один и тот же IP
> посчитается разными адресами и глобальная агрегация не сработает.

## 4. Применение бана (`enforce`)

1. Запись в таблицу `antifraud_bans` (upsert по email) — бан переживает рестарт процесса.
   Если запись не удалась, дальнейшие шаги отменяются: несогласованное состояние хуже бана.
2. Обновление in-memory `banStore`.
3. Hot-remove пользователя из Xray через gRPC (ошибка не фатальна).
4. На мастере — рассылка `rmuser` на слейвы (fire-and-forget).

Пока бан активен, подписка отдаёт только «профили-заглушки»
(`subscription.dummy_configs.anti_fraud`) с заголовком `X-Reject-Reason: antifraud_ban`:
реальные outbound'ы не генерируются, что исключает попытки подключения и лишнюю нагрузку
на TLS-хендшейки.

### Режим `dry_run`

При `anti_fraud.dry_run: true` факт нарушения только логируется (не чаще одного раза в
минуту на пользователя), баны не применяются. Рекомендуется первые сутки после включения
модуля работать именно так и оценить ложные срабатывания.

## 5. Снятие бана

`unbanCleaner` каждые 15 секунд ищет истёкшие баны и соблюдает защиту от «пользователей-
призраков»:

1. удалить запись бана (фиксация намерения);
2. проверить, что пользователь всё ещё есть в конфиге;
3. проверить, что `subscriptions.status == "active"` (подписка могла истечь во время бана);
4. только после этого вернуть клиента в Xray.

Администратор может снять бан немедленно: `ForceUnban(email)` вызывается из
`POST /api/v1/admin/users/{email}/unblock` и из CLI `unlimit`.

При старте процесса выполняется восстановление: все неистёкшие баны из БД снова
применяются к рантайму.

## 6. Кластерный режим

* **Слейв** (`report_to_master: true`): накапливает события и отправляет их мастеру пачками
  раз в 5 секунд действием `antifraud-events`. Локально решение о бане **не принимается** —
  слейв не знает `max_devices` пользователей.
* **Мастер** (`anti_fraud.enabled: true`): принимает события слейвов через
  `POST /api/v1/internal/xray/sync`, добавляет их в общий счётчик и принимает единое решение
  по всему кластеру. Активные слейвы (те, что отчитывались последние 5 минут) видны в снапшоте.

## 7. Ротация access-лога

Ротатор переименовывает лог в `*.old` при превышении `log_rotation_size_mb` или
`log_rotation_max_age`, сигнализирует Xray переоткрыть файл (LoggerService по gRPC), даёт
tailer'у дочитать хвост и удаляет `.old`, освобождая RAM. При старте найденные «осиротевшие»
`.old`-файлы удаляются.

Файл лога **обязан** лежать в RAM-ФС (`/dev/shm`): при интенсивном трафике запись на диск
быстро изнашивает SSD и создаёт I/O-задержки.

## 8. Наблюдение

```bash
# Живой снимок: пользователи, число активных IP-хешей, количество активных слейвов
xraytool ips

# То же самое через API
curl -s -H "X-API-Key: $KEY" https://master/api/v1/admin/antifraud/state
```

Полезные строки лога: `antifraud: fraud detected`, `antifraud: ban applied`,
`antifraud rotator: log rotated`, `antifraud recovery: re-applying active bans from DB`.

## 9. Рекомендуемые настройки

```yaml
anti_fraud:
  enabled: true
  dry_run: false
  log_path: /dev/shm/xray-access.log
  max_ips: 3            # запас на мобильные сети, IPv4+IPv6 и CGNAT
  ip_limit_ttl: 3m
  ban_duration: 10m
  log_rotation_size_mb: 20
  log_rotation_max_age: 5m
  salt_secret: "одна_и_та_же_соль_на_всех_узлах"
```

В конфиге Xray-core должен быть включён access-лог в тот же путь:

```json
"log": { "access": "/dev/shm/xray-access.log", "loglevel": "warning" }
```
