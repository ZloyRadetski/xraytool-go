# Полное руководство по архитектуре и механике XrayTool Go

Данный документ представляет собой глубокий code review и подробное описание всех механизмов работы проекта `xraytool-go`. Проект представляет собой гибридную систему управления VPN-сервером на базе Xray, объединяющую в себе CLI-инструментарий и высокопроизводительный REST API бэкенд.

---

## 1. Общая Архитектура Проекта

Проект `xraytool-go` написан на языке Go и имеет единый бинарный файл (`xraytool-server` / `xraytool`), который может запускаться в двух режимах:
1. **CLI (Command Line Interface)**: Выполнение разовых команд управления (например, `xraytool newuser`, `xraytool unlimit`). Интерфейс построен на библиотеке Cobra.
2. **REST API Server (Daemon)**: Полноценный веб-сервер, который работает в фоне (как systemd-сервис), слушает порт (обычно 8080) и обрабатывает запросы на получение подписок (`/client`), а также запросы управления от сторонних ботов.

### Ключевые директории и пакеты:
- `cmd/` — логика командной строки и инициализация веб-сервера.
- `internal/subscription/` — ядро сервиса: выдача подписок, работа с кэшем, лимиты устройств.
- `internal/xrayconfig/` — парсер и манипулятор конфигурационным файлом `config.json` ядра Xray.
- `internal/xrayapi/` — gRPC клиент для «горячего» управления Xray без перезагрузки.
- `internal/database/` — экспериментальный модуль SQL (на данный момент используется гибридный файлово-SQL подход, с предпочтением файлового кэша).

## 2. Взаимодействие CLI и Бэкенда

В классических PHP/Bash сборках боты дёргали bash-скрипты на каждый чих. В `xraytool-go` реализована гибридная система маршрутизации команд (`cmd/server.go`), которая обеспечивает максимальную скорость и обратную совместимость.

Когда Nginx проксирует POST запрос от Telegram-бота на `/api/rest/xraytool/{command}`:

1. **Direct Execution (Прямое выполнение в памяти)**:
   Самые частые и тяжелые команды (`newuser`, `unlimit`, `setexpire`, `setlimit`) перехватываются сервером и выполняются **напрямую в его адресном пространстве**.
   - Сервер не запускает сторонние процессы (`exec`), что экономит CPU.
   - Изменения применяются мгновенно.
2. **Fallback Mechanism (Вызов CLI)**:
   Если команда не поддерживается прямым выполнением (например, `rmuser`, `stats`), сервер вызывает **сам себя** через `exec.CommandContext`, передавая нужные флаги. Это гарантирует 100% совместимость со старыми скриптами.
3. **Безопасность**: Запросы защищены заголовком `X-API-Key`, который сверяется с `xray_api_config.json`. Все нестандартные пути или плохие запросы логируются в Intruder Alert.

## 3. Механика Выдачи Подписок (`/client`)

Это самая нагруженная часть системы. Когда клиентское приложение (v2rayNG, Streisand, Shadowrocket) обращается по ссылке вида `https://domain.com/client?id=...`, происходит магия `CacheManager` (`internal/subscription/cache.go`).

### In-Memory Кэширование и производительность
Чтобы сервер мог выдерживать тысячи запросов в секунду, он **не читает файлы с диска** при каждом запросе.
При старте он загружает в RAM:
- Шаблоны конфигураций (`configs.txt`, `routing.json`)
- Базу лимитов (`limited_users.db`)
- Активных пользователей (парсит `config.json` от Xray и строит хэш-таблицы для доступа за O(1))
- Состояние устройств (`devices_state.json`)

**Как происходит "Горячая перезагрузка" (Hot-Reloading):**
При каждом входящем запросе вызывается `cm.Refresh()`.
Сервер делает системный вызов `os.Stat()` для отслеживаемых файлов. Эта операция занимает менее 1 микросекунды (т.к. кэшируется ядром ОС). Если сервер видит, что `ModTime` (время изменения файла) изменилось (например, бот удалил юзера или обновил файл), сервер сбрасывает часть своего кэша и перечитывает обновленный файл с диска.

### Шаблонизация (Template Engine)
Сервер берёт строку-шаблон из `configs.txt` и с помощью `strings.ReplaceAll` заменяет плейсхолдеры на реальные данные пользователя.
Например:
- `{UUID}` — ID клиента для VLESS.
- `{HOST}`, `{SNI}` — поддомены и IP сервера.
- `{HY2_AUTH}` — сгенерированный или извлеченный пароль для Hysteria2.
В итоге клиент получает либо чистый JSON-конфиг, либо набор ссылок `vless://...` (если передан параметр `format=vless`).

## 4. Система Лимитов Устройств (Device Limits & HWID)

Эта система предотвращает «шаринг» одной подписки на толпу людей (`internal/subscription/devices.go`).

### Идентификация оборудования (HWID)
1. Сервер ищет уникальный идентификатор устройства в заголовках (`X-HWID`, `X-Device-Id`, `UDID`) или параметрах URL. Поиск регистронезависимый.
2. Происходит нормализация `normalizeHwid`: строка приводится к нижнему регистру, из неё вырезаются все спецсимволы (остаются только a-z, 0-9, -, _). Это защищает от подмены HWID через пробелы или символы Unicode.

### Процесс проверки (UpdateDeviceState)
1. Сервер берёт нормализованный HWID и ищет его в своей оперативной памяти для данного пользователя (в структуре `ClientDevices`).
2. **Если HWID найден**: Сервер обновляет `LastSeen`, `RequestCount`, `DeviceOS` и пропускает клиента.
3. **Если HWID новый**:
   - Сервер смотрит на лимит устройств (например, 3).
   - Если количество уже сохранённых устройств >= 3, возвращается ошибка `limitReached = true`. Пользователь получает заглушку (Dummy Config) с надписью `🛑 Лимит устройств 🛑`.
   - Если слоты есть, устройство добавляется в оперативную память сервера.

### Синхронизация с файлом (flushDeviceStateWorker)
Так как изменения пишутся в RAM, в фоне крутится воркер, который просыпается каждые 5 секунд.
Если он видит флаг `c.deviceStateDirty == true` (появились новые устройства), он:
1. Конвертирует память в JSON.
2. Пишет данные во временный файл `devices_state.json.tmp`.
3. Делает атомарное переименование `os.Rename` в `devices_state.json`.
Это исключает ситуацию, когда сервер крашится во время записи и повреждает весь файл.

### Интеграция с ботами (Сброс устройств)
Если внешний бот (например, Telegram бот на Python/PHP) открывает `devices_state.json` и удаляет оттуда HWID, изменяется время модификации файла на диске. 
При следующем запросе подписки функция `Refresh()` замечает изменение, сбрасывает кэш устройств и перечитывает файл с диска. Таким образом, удалённые ботом устройства моментально исчезают из памяти сервера, и пользователь снова может подключать новые девайсы.

## 5. Взаимодействие с ядром Xray (Xray API & Config)

В классическом подходе любое добавление пользователя требовало перезагрузки ядра Xray (`systemctl restart xray`), что обрывало сессии всем текущим клиентам (соединения падали). 

В `xraytool-go` эта проблема решена:
1. **gRPC API (`internal/xrayapi`)**: Xray ядро открывает скрытый порт для API. Когда `xraytool-go` добавляет нового юзера (команда `unlimit` или `newuser`), он отправляет protobuf-команды `AddUser` / `RemoveUser` прямо в оперативную память Xray. Юзер начинает или перестает работать **мгновенно, без обрыва связи для остальных**.
2. **Синхронизация с диском (`internal/xrayconfig`)**: Чтобы новые юзеры не пропали при перезагрузке самого сервера, `xraytool-go` параллельно парсит файл `config.json`, находит нужные `inbounds` (VLESS, Hysteria), вставляет туда новые JSON-блоки пользователей и сохраняет файл обратно на диск.

## 6. Фоновые процессы (Workers)

- **Expiry Worker (`internal/worker/expiry.go`)**: 
  Работает каждые 60 секунд. Пробегается по всем активным юзерам (из кэша) и проверяет их поле `expire` (дату окончания). Если текущая дата больше даты expiry, воркер автоматически блокирует юзера (отправляет `RemoveUser` в Xray API и вычищает его из `config.json`), перенося в список заблокированных.
- **Статистика (Stats)**: 
  Xray API позволяет запрашивать количество потреблённого трафика в реальном времени. Статистика используется для отображения пользователям потраченного трафика прямо в названии их конфигов (например, `upload=0; download=1048576; expire=...`).
